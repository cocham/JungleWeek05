# Use-After-Free 디버깅 트러블슈팅

## 문제 상황
작은 GUI 흉내 프로그램에서, 다이얼로그 위젯이 닫기 `이벤트(code == 1)`를 받으면 스스로 `free()`한다. 하지만 `Screen`의 `포인터 배열(items[])`에서는 그 슬롯을 `정리(NULL 처리)`하지 않는다. 그 직후 상태 메시지 버퍼를 새로 `malloc`하면서 방금 해제된 메모리 공간을 다시 사용해 기존 `Widget`의 데이터를 덮어쓴다.이후 `screen_render()`에서 해당 슬롯에 남아 있던 포인터를 다시 사용하면서 `SIGSEGV`가 발생한다.

## **Step 3. `next` vs `step` 헷갈림**

디버깅하면서 `next`와 `step`의 차이를 제대로 이해하지 못해서 헷갈렸다.

```c
static void screen_dispatch(Screen *s, int code) {

    for (int i = 0; i < s->count; i++) {

        Widget *w = s->items[i];

        w->vtbl->on_event(w, code);

    }

}
```

`main`에서 `screen_dispatch(&s, 1)`을 호출한 뒤, `on_event`에 실제로 어떤 함수가 연결되어 있는지 따라가면서 확인했다.

* `next` → 현재 줄의 함수를 실행하되, 호출된 함수 안으로 들어가지 않음
* `step` → 현재 줄의 함수를 실행하고, 호출된 함수 안으로 들어감

#### 헷갈렸던 부분
![alt text](image-7.png)

`i`가 `2`인데 `w`를 확인하니 `items[1]`의 주소가 나왔다.

```gdb
print i
$22 = 2

print w
$21 = (Widget *) 0xaaaaaaac12d0

print s->items[2]
$23 = (Widget *) 0xaaaaaaac1300
```

처음에는 `i`가 2니까 당연히 `w`도 `items[2]`를 가리켜야 한다고 생각했다.

그런데 GDB가 현재 멈춰 있는 줄을 다시 확인해보니:

```text
114    for (int i = 0; i < s->count; i++) {
115        Widget *w = s->items[i];
116        w->vtbl->on_event(w, code);
```

`115번 줄`에 **도착해 있었을 뿐, 아직 실행하지 않은 상태**였다.

아직 `w = s->items[i]`가 실행되지 않았기 때문에, 현재 확인되는 `w` 값은 이번 반복의 `items[2]`에서 가져온 값이 아니다.

여기서 `next`를 한 번 더 실행해서

```c
Widget *w = s->items[i];
```

가 실행된 뒤 다시 확인하니:

```gdb
print w
$ = (Widget *) 0xaaaaaaac1300

print s->items[2]
$ = (Widget *) 0xaaaaaaac1300
```

같은 주소가 나왔다.

`next`와 `step`의 차이를 알고 디버깅 하는 게 중요하다. 또한 `print`로 변수를 확인할 때는 그 변수를 대입하는 줄이 실제로 실행됐는지 같이 봐야 한다.

## **Step 4. `free()` 발생 시점 추적**

앞에서 `screen_dispatch()`의 흐름을 확인한 뒤, 각 위젯의 `on_event`가 실제로 어떤 함수를 호출하는지 따라가 보았다.

전체적인 디버깅 순서는 다음과 같이 진행했다.

```text
run
→ screen_dispatch 진입
→ i=0부터 이벤트 처리 확인
→ i=2에서 Dialog #12 확인
→ dialog_on_event() 진입
→ widget_destroy() 호출
→ free() 실행
→ 이후 app_build_status()와 screen_render() 추적
```

### **`break screen_dispatch`**

`main()`에서 `screen_dispatch(&s, 1)`이 호출되는 지점부터 이벤트 처리를 따라가기 위해 `screen_dispatch`에 breakpoint를 걸었다.

![alt text](image-8.png)

### **i=0 (Label) 이벤트 처리 확인**

`i=0`에서는 Label 위젯이 선택되었고, `on_event` 함수 포인터를 따라가니 `widget_noop_event()`가 호출되었다.

`noop`은 **아무 작업도 하지 않는 함수**로, 여기서는 이벤트를 받아도 별도의 동작 없이 그대로 반환한다.

![alt text](image-9.png)

### **i=1 (Button) 이벤트 처리 확인**

`i=1`인 Button도 `on_event`에 `widget_noop_event()`가 연결되어 있어 별도의 동작 없이 다음 반복으로 넘어갔다.

![alt text](image-10.png)

### **i=2 (Dialog) 이벤트 처리 확인**

`i=2`에서는 Dialog #12가 선택되었다.

앞의 Label과 Button과 달리 Dialog의 `on_event`에는 `dialog_on_event()`가 연결되어 있었다.

```text
w->vtbl->on_event(w, code)
        ↓
dialog_on_event()
        ↓
widget_destroy(self)
        ↓
free(w)
```

GDB에서 `step`으로 함수 안으로 들어가면서 `dialog_on_event()`가 호출되는 것을 확인했고, 이후 `widget_destroy()`를 거쳐 `free(w)`가 실행되는 시점까지 추적했다.

즉, **Dialog #12가 이벤트 코드 `1`을 받으면 실제로 메모리에서 해제되는 것까지 확인했다.**

## **Step 5. `free()` 이후에도 포인터가 그대로 남아있음 (dangling pointer 확인)**

`free(w)`를 실행한 뒤에도 `s->items[2]`의 값이 바뀌지 않는 것을 확인했다.

```gdb
print s->items[2]

$64 = (Widget *) 0xaaaaaaac1300
```

![alt text](image-12.png)

```text
Widget 메모리        ← free됨
     ↑
     │
s->items[2]           ← 여전히 0xaaaaaaac1300을 가리킴
```

`free()`는 **포인터가 가리키던 메모리를 해제할 뿐, 그 포인터 변수의 값을 자동으로 NULL로 바꾸지는 않는다.**

```c
widget_destroy(self);
        ↓
free(self);
```

따라서 free(w)를 통해 w가 가리키던 Widget 메모리는 해제됐지만, 

```c
s->items[2]
```

s->items[2]에 저장된 주소값은 그대로 남아 있다.

```text
0xaaaaaaac1300
```


이처럼 **해제된 메모리를 계속 가리키고 있는 포인터를 dangling pointer라고 한다.**

> 이 시점에서는 아직 크래시가 발생하지 않았다.

## **Step 6. `malloc()`이 같은 주소를 재사용하고 기존 데이터가 덮어써지는 과정 추적**

`screen_dispatch()`에서 `Dialog`가 `free()`된 뒤, `main()`으로 돌아와 `app_build_status()`가 호출되는 과정을 따라갔다.

```gdb
finish
```

`main()`에서 다음 코드에 도착한다.

```c
char *status = app_build_status("dialog closed");
```

### **`app_build_status()` 내부 확인**

`step`으로 함수 안으로 들어가 `malloc()`부터 순서대로 확인했다.

![alt text](image-13.png)

`app_build_status()`에서는 다음과 같이 `Widget`과 같은 크기로 메모리를 할당한다.

```c
char *msg = malloc(sizeof(Widget));
```

이후 할당된 메모리에 `0xAB`를 채우고,

```c
memset(msg, 0xAB, sizeof(Widget));
```

`snprintf()`를 통해 `"STATUS: dialog closed"`를 저장한다.

```c
snprintf(msg, sizeof(Widget), "STATUS: %s", text);
```

여기서 **`malloc()`이 어떤 주소를 반환했는지** 확인했다.

---

### **`status`와 `s->items[2]`의 주소 비교**

`app_build_status()`가 끝난 뒤 `status`와 기존 `s->items[2]`의 주소를 확인했다.

![alt text](image-14.png)


`status`와 `s->items[2]`가 **둘 다 `0xaaaaaaac1300`을 가리키고 있고, 비교 결과도 `1`**이 나왔다.

즉,

```text
Dialog #12가 사용했던 주소
        ↓
0xaaaaaaac1300
        ↓
free()
        ↓

        ↓
0xaaaaaaac1300 재사용
        ↓
status
```

처럼 **방금 해제된 메모리 공간이 다시 `status`에 할당된 것**을 확인했다.

---

### **기존 Widget 데이터가 덮어써진 상태 확인**

같은 주소를 `s->items[2]`를 통해 다시 읽어봤다.

![alt text](image-15.png)

원래 이 주소에는 Dialog #12의 데이터가 들어 있었지만, 현재는 값이 달라져 있다.


원래 Dialog의 `id`는 `12`였고 `vtbl`도 `DIALOG_VT`를 가리키고 있었지만, 지금은 전혀 다른 값이 들어가 있다.

메모리 전체를 확인해보면:

```gdb

```

```text

```

처럼 `STATUS` 문자열과 `0xAB` 패턴이 들어가 있는 것을 볼 수 있다.

`memset()`으로 메모리 전체를 `0xAB`로 채운 뒤, `snprintf()`가 앞부분을 `"STATUS: dialog closed"` 문자열로 덮어썼다. 따라서 문자열 이후의 남은 공간에는 `0xAB` 값이 그대로 남아 있는 것을 `GDB`에서 확인할 수 있었다.

**즉, 원래 Dialog가 사용하던 메모리 공간을 `status`가 다시 사용하면서 기존 `Widget`의 내용이 덮어써진 것이다.**

## **Step 7. 해제된 메모리를 다시 사용하면서 `SIGSEGV` 발생**

이제 `main()`에서 다시 `screen_render()`가 호출되는 과정을 따라갔다.

```c id="r1x0xq"
printf("frame 2:\n");

screen_render(&s);
```


`screen_render()` 내부에서는 다시 `s->items[i]`에서 위젯을 가져와 `render` 함수 포인터를 호출한다.

![alt text](image-16.png)

```c id="79leaq"
for (int i = 0; i < s->count; i++) {
    Widget *w = s->items[i];
    w->vtbl->render(w);
}
```

`i == 2`인 경우에 멈추도록 breakpoint를 걸었다.

```gdb id="gk7c8d"
break 123 if i == 2
```

![alt text](image-17.png)

`i == 2`가 되면 `w = s->items[2]`를 통해 **앞에서 이미 `free()`된 Dialog의 주소를 다시 가져오게 된다.**

![alt text](image-18.png)
*크래시 발생 직전 `w->vtbl` 확인*


그리고 바로 다음 줄의:

```c id="vfs1n7"
w->vtbl->render(w);
```

을 실행하자,

```text id="5p1j4a"

```

가 발생했다.

즉, `screen_render()`에서 이미 해제되고 다른 데이터로 덮어써진 메모리를 `Widget`으로 사용하면서 SIGSEGV가 발생한 것이다.

## **결론**

문제는 `Dialog`가 `free()`된 뒤에도 `Screen`의 `items[2]`에 **해제된 Widget의 주소가 그대로 남아 있었다는 것**이다. 이후 같은 메모리가 다른 용도로 재사용되면서 기존 Widget의 내용까지 덮어써졌고, `screen_render()`에서 해당 포인터를 다시 사용하면서 `SIGSEGV`가 발생했다.

---

## **개념 정리**

### **포인터는 메모리 주소를 저장한다**

```c
Widget *w = s->items[2];
```

여기서 `w`에는 Widget 객체 자체가 들어있는 것이 아니라, **Widget이 저장된 메모리 주소가 들어있다.**

C에서는 `free()`를 통해 해당 메모리를 해제한 뒤에도, 다른 포인터가 그 주소를 가지고 있는지 자동으로 찾아서 바꿔주지 않는다.


문제는 이 상태에서 다시:

```c
w->vtbl->render(w);
```

처럼 접근하면, **이미 해제됐거나 다른 데이터로 재사용된 메모리를 여전히 Widget이라고 생각하고 사용하게 된다는 것**이다.

# **수정방향**

### **`dialog_on_event()`에서 직접 `items[2] = NULL`을 할 수 없는 이유**

```c
static void dialog_on_event(Widget *self, int code) { ... }
```

`dialog_on_event()`가 받는 것은 `self`와 `code`뿐이다.

```c
Widget *self
```

을 통해 자기 자신인 Widget에는 접근할 수 있지만, 이 Widget을 가리키고 있는 `Screen`이나 `items[]` 배열에 대해서는 알 수 없다.

따라서 여기서:

```c
widget_destroy(self);
```

까지 해버리면 메모리는 해제되지만, `Screen`에 남아 있는 포인터까지 같이 정리할 수 없다.

그래서 Dialog에서는 **"닫혔다"는 상태만 표시하고**, 실제 메모리 해제와 슬롯 정리는 `Screen`에서 담당하도록 수정한다.

---

### **Screen에서 정리하는 이유**

`Screen`이 `items[]`를 통해 `Widget`의 포인터를 관리하고 `dispatch`와 `render`에서도 이를 순회하므로, `Widget`의 수명 관리도 `Screen`에서 담당하도록 한다.

```text
dialog_on_event()
→ closed = 1로 상태만 변경

screen_cleanup_closed()
→ 실제 free()
→ 해당 슬롯 NULL 처리
```

이렇게 **메모리 해제와 그 포인터의 무효화를 한 곳에서 같이 처리**하면, `free()`한 뒤 슬롯을 정리하지 않는 실수를 줄일 수 있다.

---

### **`dispatch` / `render`에서 NULL 체크를 하는 이유**

이제 닫힌 Widget을 정리하면:

```c
s->items[i] = NULL;
```

인 슬롯이 생긴다.

따라서 이후 `items[]`를 순회하는 `screen_dispatch()`와 `screen_render()`에서는 빈 슬롯을 만났을 때 건너뛰어야 한다.

```c
if (!w) continue;
```

이 체크가 있어야 `NULL`인 슬롯에 대해:

```c
w->vtbl
```

처럼 접근하는 것을 막을 수 있다.

---

# **수정 코드**

### **① `dialog_on_event()`에서는 상태만 변경**

```c
static void dialog_on_event(Widget *self, int code) {
    if (code == 1) {
        self->closed = 1;
        // widget_destroy(self);  ← 삭제
    }
}
```

기존에는 여기서 바로:

```c
widget_destroy(self);
```

를 호출했지만, 이제는 Dialog가 직접 `free()`하지 않는다.

---

### **② Screen에서 닫힌 Widget을 정리하는 함수 추가**

```c
static void screen_cleanup_closed(Screen *s) {
    for (int i = 0; i < s->count; i++) {
        Widget *w = s->items[i];

        if (w && w->closed) {
            widget_destroy(w);
            s->items[i] = NULL;
        }
    }
}
```

`closed`인 Widget을 찾으면:

```text
widget_destroy(w)
      ↓
    free(w)

s->items[i] = NULL
```

순서로 처리한다.

이제 **메모리를 해제한 뒤 그 주소를 계속 가지고 있는 상태가 남지 않도록** 같은 곳에서 함께 처리한다.

---

### **③ `dispatch` / `render`에서는 NULL 슬롯 건너뛰기**

```c
static void screen_dispatch(Screen *s, int code) {
    for (int i = 0; i < s->count; i++) {
        Widget *w = s->items[i];

        if (!w) continue;

        w->vtbl->on_event(w, code);
    }
}
```

```c
static void screen_render(Screen *s) {
    for (int i = 0; i < s->count; i++) {
        Widget *w = s->items[i];

        if (!w) continue;

        w->vtbl->render(w);
    }
}
```

## **`main()` 수정**

```c
screen_dispatch(&s, 1);

screen_cleanup_closed(&s);   // dispatch 직후 추가

char *status = app_build_status("dialog closed");

printf("%s\n", status);

printf("frame 2:\n");

screen_render(&s);

free(status);

for (int i = 0; i < s.count; i++) {
    if (s.items[i])
        free(s.items[i]);
}
```

`screen_dispatch()`에서 닫힌 Widget을 표시한 뒤 바로 `screen_cleanup_closed()`를 호출해서 해당 Widget을 정리한다.

이후 `screen_render()`에서는 이미 해당 슬롯이 `NULL`이므로 건너뛰게 된다.

마지막 `for`문에서도 `NULL` 체크를 해두면 이미 정리된 `items[i]`를 다시 `free()`하는 것을 피할 수 있다.

---

## **검증**

```bash
make gdb NAME=01_use_after_free
run
```

수정 후에는 다음을 확인한다.

* 프로그램이 `SIGSEGV` 없이 종료된다.
* `frame 2:` 이후 `<<Dialog #12>>`는 출력되지 않는다.
* Label, OK, Cancel만 출력된다.

`AddressSanitizer`로도 다시 확인한다.

```bash
-fsanitize=address
```

수정 전에는 `heap-use-after-free`와 관련된 오류를 확인할 수 있었지만, 수정 후에는 해당 오류가 더 이상 발생하지 않는지 확인한다.

---

## **핵심 정리**

```text
Dialog가 직접 free()
        ↓
Screen에는 해제된 주소가 그대로 남음
        ↓
dangling pointer 발생
        ↓
같은 메모리가 status에 재사용됨
        ↓
기존 Widget 데이터가 덮어써짐
        ↓
screen_render()에서 다시 사용
        ↓
SIGSEGV
```

수정 후:

```text
Dialog
  ↓
closed = 1

  ↓

Screen cleanup
  ↓
free(w)
  ↓
s->items[i] = NULL

  ↓

screen_render()
  ↓
NULL 슬롯은 건너뜀
```
